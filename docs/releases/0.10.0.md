# MemoryWhale 0.10.0 — Agent-Native Memory

**Release date: September 6, 2026**

**Product: 0.10.0 · Rust core: 0.5.0 · SQLite schema: 10**

MemoryWhale keeps debugging evidence usable when you switch terminals,
worktrees, or coding agents. This release adds installable Claude Code and Rho
adapters, explicit producing-agent metadata, repository identity, and local
HTTP interfaces. It remains a local debugging-memory layer, not an autonomous
coding agent.

The CLI, web UI, and desktop app use product version **0.10.0**.
`memorywhale-core` has its own version, **0.5.0**, because its public Rust
`Memory` type changes in this release.

## Install or upgrade

Prebuilt binaries cover Linux x86_64/aarch64 and macOS. The installer resolves
the current published release and verifies its published checksum:

```bash
(
  set -eu
  installer="$(mktemp)"
  trap 'rm -f "$installer"' EXIT
  curl -fsSL https://raw.githubusercontent.com/wuisabel-gif/MemWhale/7c3864c743cec9a8fa813dcc0b2459cc2859c849/install.sh -o "$installer"
  printf '%s  %s\n' '3e0cad72b29c1894d5ff5f7c30b099537f96501801c14b6320c12e169a3ac8d6' "$installer" | shasum -a 256 -c -
  sh "$installer"
)
```

To request this exact CLI release from crates.io:

```bash
cargo install memorywhale-cli --version 0.10.0 --locked
```

Or use Homebrew:

```bash
brew tap wuisabel-gif/memorywhale https://github.com/wuisabel-gif/MemWhale
brew install memorywhale
# If already installed:
brew update
brew upgrade memorywhale
```

The installer and Homebrew track their published release metadata rather than
pinning this document's version; check what was installed. Make sure the chosen
binary directory is on `PATH` (`~/.local/bin` for the installer or
`~/.cargo/bin` for Cargo):

```bash
mw --version
mw doctor
```

From a source checkout, build all helpers from the repository root:

```bash
cargo build --release -p memorywhale-cli --bins
```

The CLI does not require the desktop shell's GTK/WebKit libraries. Windows
users can use WSL. See [Getting started](../guides/getting-started.md) and the
[Linux guide](../../linux/README.md) for platform setup and Debian packaging.

The bootstrap above needs `curl` and `shasum`; it pins and verifies the installer
before execution. The installer then selects the latest published binary release.
Native Windows is not supported by `mw github context`; it fails before spawning
`gh`. Use the Linux build under WSL for deadline-safe subprocess capture.

## What changed

The changes fit the four areas in the [architecture](../architecture.md):

### Capture: installable, inspectable agent adapters

```bash
mw integrate claude
mw integrate rho
mw doctor
```

The Claude Code and Rho installers configure MCP registration, a bundled
memory-use skill, and Rust-backed hooks through `mw-remember --from-hook`.
They need neither a repository checkout nor the previous Python capture
script. `--revert` removes MemoryWhale's integration components without
deleting the database. Installation preserves unrelated configuration and
reports conflicts rather than silently replacing it. (#230)

`mw doctor` now reports MCP registration, automatic-capture hooks, and skills
independently for each client. An absent optional client is `not detected`,
not a broken MemoryWhale install. Doctor honors `CLAUDE_CONFIG_DIR` and
`RHO_HOME`; its bounded MCP probe negotiates the protocol and lists tools,
without calling memory tools, running client CLIs, or editing their config.
(#245)

**Capture fidelity matters.** The current Rho hook payload lacks shell command
text, process exit code, and stdout. Failed or unavailable calls can be kept
as metadata with a `[rho:after_tool_use]` sentinel instead of an invented
command. Successful calls without command text are skipped. Hooks preserve
available evidence; installing MCP alone does not capture terminal activity.
See the [Claude Code](../../integrations/claude-code/README.md) and
[Rho](../../integrations/rho/README.md) guides for the supported payloads.

### Memory: repository/worktree identity and schema 10 provenance

Schema 9 adds `repository_id`, `repository_name`, and `worktree_root` to
commands and sessions. Repository discovery reads local Git metadata without
running Git or contacting a remote. A normalized origin identifies the
repository when available; otherwise the local common Git directory is the
fallback. Linked worktrees share a canonical repository ID but retain their
own worktree roots. Existing project tags remain useful and are not replaced
by repository identity. Historical paths are backfilled only when local
metadata can still be resolved. (#234)

Schema 10 adds nullable `command_runs.agent`. Supported hook capture records
`claude` or `rho`; terminal/manual captures and legacy rows retain SQL `NULL`.
The UI/filter label for that null value is `terminal`. It is not proof of human
authorship, and the literal string `terminal` is not the stored representation.
The migration does not guess an agent from free-form notes. (#256)

**Agent is separate from source.** A Claude-captured shell command is still a
`command` source, not a new `claude` source. Sessions and notes keep their
existing source types. MCP note author information is separate from the
structured producing-agent field on command captures.

### Retrieval: follow evidence across agents

```bash
mw search "linker error" agent:claude
mw search "linker error" agent:rho
mw search "linker error" agent:terminal
```

Agent metadata and labels are exposed through CLI output, TUI, dashboard,
desktop, JSON API, and MCP. Agent filters can be combined with existing source,
project, machine, date, and tag filters where those interfaces support them.
MCP `search_memory` and `get_context` accept an optional `agent` argument;
JSON API search accepts an `agent` query parameter. The accepted values are
`claude`, `rho`, and `terminal`. (#257)

### Interfaces: local HTTP MCP and opt-in JSON API

`mw-mcp` remains the stdio interface with the same six tools:
`recent_errors`, `search_memory`, `get_context`, `remember`, `similar_failures`,
and `stats`. Protocol revision `2026-07-28` adds per-request metadata and
`server/discover`; legacy `2025-11-25` and `2024-11-05` initialization remain
supported. (#233)

`mw-serve` exposes those tools at **`POST /mcp`** on the dashboard listener.
It handles one JSON-RPC object per POST, not an SSE session. Rho can select
that endpoint with `mw integrate rho --http [url]`; stdio remains the default.
(#241)

```bash
mw-serve --api
```

The **read-only `/api/v1` JSON API is disabled unless `--api` is supplied**.
It provides health, search, memory-by-ID, command-by-ID, sessions, and canonical
repository/worktree endpoints. Lists/searches are bounded to 50 items, with
versioned JSON envelopes and an OpenAPI contract. There are no API write,
arbitrary SQL, or arbitrary filesystem-read endpoints. `POST /mcp` is
independent of `--api`; its `remember` tool can explicitly save a lesson,
pending review by default. (#236)

Loopback access is open by default unless a token is explicitly configured.
Non-loopback serving requires a token; `--lan` can mint a persistent
`serve.token`. Protected MCP requests require `Authorization: Bearer <token>`;
protected JSON API requests accept Bearer authentication or the dashboard
login cookie. Cleartext HTTP does not encrypt your data or token: keep it on a
trusted network or protect the connection. See the [MCP reference](../reference/mcp.md),
[JSON API reference](../reference/api.md), and [security model](../SECURITY.md).

### Explicit read-only GitHub context

```bash
mw github context 123
```

Run this in the repository whose PR you want to inspect. It delegates
authentication to your existing `gh` login and fetches PR metadata, CI
check-runs, classic commit statuses, and reviews only when requested. Check-runs
and commit statuses use separate GitHub endpoints; neither is treated as a
substitute for the other. Output is bounded and redacted, and subprocess
runtime is capped. Unavailable optional sections are identified without hiding
the PR metadata.
Treat fetched text as untrusted external evidence. (#260, with release-branch
status and subprocess hardening)

**The command prints context; it does not automatically save it.** It does
not check out or execute PR code, submit a review, or continuously synchronize
GitHub. To retain a conclusion, explicitly save a reviewed summary with
`mw remember`. If you run the command inside a captured terminal or under
`mw-run`, your existing capture policy can record its output independently.

## Upgrade and Rust compatibility

- Back up your store before upgrading. Existing databases migrate additively
  through schema 9 and 10 when opened by the new CLI; original evidence rows
  remain in place. Old rows keep null agent attribution.
- Re-run the integration installer if you used older manual/Python hooks,
  then restart the client and inspect `mw doctor`. A healthy MCP server does
  not by itself confirm a capture hook or skill is installed.
- **Breaking Rust API:** `memorywhale_core::Memory` gains the public
  `agent: Option<String>` field. Existing struct literals must include
  `agent: None` for unknown/terminal provenance, or an appropriate canonical
  value for known structured command capture.
- **Serialized compatibility:** the new field has `#[serde(default)]`, so
  older serialized memories that omit `agent` still deserialize as `None`.
  This does not remove the compile-time requirement on Rust struct literals.
- Core `0.5.0` is separate from product `0.10.0`. The post-v0.9.0 packaging
  correction published core `0.4.0` and fixed the CLI dependency before this
  subsequent core API change. (#224)

## What the demo and automation do not promise

The [cross-agent handoff demo](../guides/cross-agent-handoff.md) imports
sanitized Claude failure/success fixtures and uses a **simulated Rho client**
against the real `mw-mcp` stdio server and a temporary SQLite store. It checks
capture, attribution, filtering, and retrieval; Python 3 validates response
IDs, protocol/tool errors, and both failure/fix records. The demo requires
Bash and Python 3, while the installed Rust hooks do not require Python.
It does not launch Rho or
Claude Code, run a provider, execute the fixture's Cargo command, or verify
that the fixture's proposed fix actually works. (#258)

Task-start recall, automatic failure lookup, and pre-compaction lesson saving
are a documented direction for client orchestration, **not implemented
lifecycle automation in 0.10.0**. The shipped hooks capture supported events;
skills guide memory use; the agent/client still decides when to call retrieval
and explicit-save tools. There is no guaranteed autonomous task/failure/
pre-compaction loop. (#262)

## Documentation and release maintenance

- Integration guides now use a consistent setup/verify/capabilities/uninstall
  structure and distinguish MCP access, capture, and guidance. (#246)
- README locale synchronization checks source hashes, structure, commands,
  links, and images. Provider-backed translation is opt-in and requires
  credentials. Synchronized translations are not a claim of native-speaker
  or independent human review. (#242)
- The optional Second-Opinion CI reviewer runs only when `REVIEW_API_KEY` is
  configured; without it, the workflow warns and skips the review. Adding the
  workflow does not mean a review actually ran. It reads the diff through the
  GitHub API rather than checking out PR-head code. (#240)
- Release publication was repaired after v0.9.0, unavailable Homebrew PR
  creation no longer blocks the remaining release work, and memory-audit data
  directories are scoped to the steps that consume them. (#224–226, #261)
