# MemoryWhale 0.24.0 — Sharper Search

**Release date: October 29, 2026**

**Product: 0.24.0 · Rust core: 0.11.0 · SQLite schema: 17 (unchanged)**

Search gets two fixes, both found while checking MemoryWhale under two new
agent stacks. A real match inside a filtered search (failures only, lessons
only, or one project) no longer reads as a 0% keyword match. A failing
command now shows its error line in results, instead of the banner or rule
its output opened with. This release also adds a tested OpenHands SDK
harness and a MemoryWhale playbook for pstack's `why` and `recall` skills.

The CLI, web UI, and desktop app use product version **0.24.0**.
`memorywhale-core` moves to **0.11.0**. The store stays at schema **17**, so
nothing migrates.

## Install or upgrade

### The CLI

Prebuilt binaries cover Linux x86_64/aarch64 and macOS. The installer resolves
the current published release and verifies its published checksum:

```bash
(
  set -eu
  installer="$(mktemp)"
  trap 'rm -f "$installer"' EXIT
  curl -fsSL https://raw.githubusercontent.com/wuisabel-gif/MemWhale/7c3864c743cec9a8fa813dcc0b2459cc2859c849/install.sh -o "$installer"
  printf '%s  %s\n' '3e0cad72b29c1894d5ff5f7c30b099537f96501801c14b6320c12e169a3ac8d6' "$installer" | shasum -a 256 -c -
  sh "$installer"
)
```

To request this exact CLI release from crates.io after it is published:

```bash
cargo install memorywhale-cli --version 0.24.0 --locked
```

Or use Homebrew:

```bash
brew tap wuisabel-gif/memorywhale https://github.com/wuisabel-gif/MemWhale
brew install memorywhale
# If already installed:
brew update
brew upgrade memorywhale
```

The installer and Homebrew track their published release metadata rather than
pinning this document's version; check what was installed:

```bash
mw --version
mw doctor
```

From a source checkout, build all helpers from the repository root:

```bash
cargo build --release -p memorywhale-cli --bins
```

## What changed

### Real matches keep their keyword score in filtered searches (#463)

Search builds its keyword index over the memories it was asked to search, and
most searches are filtered: `mw search` with a project, MCP's
`search_memory` with `mode: "failures"` or `"lessons"`, the TUI, the
dashboard, and the desktop app. BM25 weights a word by how rare it is in
those rows, and gives it almost no weight once it appears in half of them.
So two failing runs of `cargo test -p calc`, searched for "calc add" among
failures, both scored a 0% keyword match.

A row that matches now keeps at least its plain word overlap with the query,
counting its tags as well as its text. Rows that don't match are unchanged.
On the retrieval benchmarks, recall@1, recall@5, and MRR are the same for
every system on both question sets.

### Failing commands lead with their error line (#464)

A search result shows the first line of a memory, and for a command that
line ended with the first line of its error output. Test runners and build
tools often start with a banner or a rule, so a failing `python3 -m unittest`
showed up as:

```
- [command #3] 57% — python3 ["python3","-m","unittest","-q"] os:macos runtime:host ======================================================================
```

MemoryWhale now moves the error line, the first one naming an error, to the
front:

```
- [command #3] 57% — python3 ["python3","-m","unittest","-q"] os:macos runtime:host AssertionError: -1 != 5 : calc-add-MWOH7
```

The CLI, TUI, MCP, dashboard, and desktop app all show it. Only the line
order changes, so every search score stays the same. Error fingerprints are
unchanged.

### OpenHands SDK, tested on synthetic stores (#456, #457)

`scripts/verification/openhands-mcp/` runs `mw-mcp` under the real OpenHands
Software Agent SDK (`openhands-sdk` 1.58.2). It never opens your store: it
uses temporary synthetic stores and a temporary `HOME`. Twelve tests cover:

- **Discovery and dispatch:** the SDK lists the six tools and calls them.
- **A fix handoff:** a lesson that claims "verified" counts only as a hint.
  A note is saved only when the harness's own fresh test run passes, and it
  stays pending until approved.
- **Isolation:** one store never returns another store's data, and each
  negative test has a positive control.

The [OpenHands guide](../../integrations/openhands/README.md) now says three
things it got wrong or left out before:

- Always set `MEMORYWHALE_DATA_DIR` in `MCPServer.env`. The server does not
  inherit it, and without it `mw-mcp` opens the default store under `HOME`.
- With one server, tool names are not prefixed by the config key.
- A read-only `filter_tools_regex` is enforced by the SDK, not by `mw-mcp`.

An opt-in `live_check.py` runs the same setup with a real model. It refuses
to run unless you set `MW_OPENHANDS_LIVE=1` and `LLM_MODEL`.

### A MemoryWhale playbook for pstack (#458)

[pstack](https://github.com/cursor/plugins/tree/main/pstack), Lauren Tan's
skill stack, sends one investigator per evidence source when its `why` skill
runs, and `recall` reuses them to ask what was tried and didn't hold.
[`integrations/pstack/`](../../integrations/pstack/README.md) adds a
read-only MemoryWhale playbook in pstack's format, filed under error tracking.
It reads lessons as unverified claims and treats "a later run succeeded 1 of
2 times" without "the latest run is green" as a fix that did not hold. A
check runs each of its calls against `mw-mcp` on a synthetic store.

## Upgrade and compatibility

- Nothing migrates. Stores stay at schema 17.
- `memorywhale-core` 0.11.0 adds `sqlite::salient_error_line`. For a matching
  row, keyword similarity is now never lower than its word overlap, so
  scores in small or filtered sets can rise. A command memory's `text` lists
  its error line first; code that parses that text sees the stderr lines
  reordered.
- Error fingerprints and recall notes are unchanged.

## What this release does not promise

- `search_memory` still returns its top rows when nothing matches, and the
  `reasons:` line names only signals of 15% or more.
- LongMemEval was not rerun for the keyword change; it needs a dataset
  download. The two bundled retrieval benchmarks were.
- No pstack `why` or `recall` run has loaded the playbook yet.
- The OpenHands live check has not been run with a real model, and container
  and remote runtimes are untested.
- The macOS app is not notarized, so the first open needs **Open Anyway**.
